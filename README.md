# SPG-023MK — ПО управления испытательным стендом амортизаторов

Настольное приложение (Windows, PySide6) для управления испытательным стендом
SPG-023MK: разгон/торможение амортизатора через частотные преобразователи,
чтение усилия/перемещения/температуры по Modbus, построение графиков испытаний
и ведение архива результатов.

> Этот README собран по факту чтения кода (сентябрь 2026) как отправная точка
> для дальнейшей поддержки. Раздел [«Известные проблемы»](#известные-проблемы-и-todo)
> — самое важное: там баги, подтверждённые реальными логами стенда.
>
> План работ по стабилизации стенда (чтение буфера, определение движения,
> доводка до НМТ) — [STABILITY_PLAN.md](STABILITY_PLAN.md).

## Что делает стенд

Амортизатор зажимается между траверсой (подвижная каретка, задаёт исходную
точку под конкретную длину амортизатора) и приводом, который циклически
двигает шток через кривошипный механизм. Стенд меряет усилие на штоке,
перемещение штока и температуру (двух точек), пока привод крутится с
заданной скоростью, и по данным одного или нескольких циклов строит график
усилие/перемещение (и производные от него: усилие/скорость, усилие/температура
и т.д.).

Управляют этим два частотных преобразователя (ЧП, «Evra» или «Delta» — выбор
в конфиге) через один и тот же COM-порт:
- адрес 1 — приводной двигатель (крутит кривошип/шток);
- адрес 2 — привод траверсы (позиционирование по высоте).

## Архитектура

```
main.py
 └─ AppWindow (app/wins/view.py)       — главное окно, графики, кнопки
     ├─ Model (scripts/model.py)       — состояние стенда, данные испытания,
     │                                    парсинг Modbus-ответов, запись команд
     ├─ Controller (scripts/controller/controller.py)
     │                                  — конечный автомат испытания (Stage)
     │   ├─ AlarmSteps                 — обработка аварий
     │   └─ TraverseService            — позиционирование траверсы
     └─ дочерние окна (архив, амортизаторы, операторы, настройки)

Model
 ├─ Client (scripts/modbus/client.py)       — pymodbus RTU-клиент, COM-порт
 ├─ Reader (scripts/reader.py)              → ReaderThread (my_thread/thread_reader.py)
 ├─ Writer (scripts/writer.py)              → WriterThread (my_thread/thread_writer.py)
 ├─ WriterArch (scripts/archive_saver.py)   — запись CSV в archive/ (свой фоновый поток)
 ├─ ParserSPG023MK (scripts/parser/parser.py) — регистры → физические величины
 ├─ CalcData (scripts/data_calculation.py)    — математика (усреднение циклов,
 │                                               мощность, частота поршня и т.д.)
 └─ CycleCollector (scripts/controller/cycle_collector.py)
                                               — детектор циклов/разворотов штока,
                                                 усреднение, точное позиционирование
```

`Reader`/`Writer` — это диспетчеры очереди в главном Qt-потоке;
сама работа с портом (чтение регистров, отправка команды ЧП) выполняется в
фоновых `QRunnable`-задачах (`ReaderThread`, `WriterThread`) из
`scripts/my_thread/`, а результат прилетает обратно через Qt-сигналы
(thread-safe). `WriterArch` пишет архив в одном своём фоновом потоке через
`queue.Queue` (см. [Архив и логи](#архив-и-логи)).

## Поток данных

1. `ReaderThread` в фоновом потоке непрерывно читает 14 holding-регистров с
   `0x2000` (усилие, перемещение, биты состояния, температуры, счётчик) —
   режим `'reg'`.
2. Во время активного испытания (`buffer_on`, бит 0 регистра `0x2003`)
   переключается в режим `'buffer'` и вычитывает кольцевой буфер осциллограммы
   с `0x4000` — по 20 записей × 6 регистров за раз, отслеживая
   последовательность по счётчику записи, пока `Model`/`CycleCollector` не
   соберут нужное число циклов.
3. `Model._reader_result` парсит ответ через `ParserSPG023MK`, обновляет
   `state_dict`/`switch_dict`, и в режиме буфера передаёт поток точек в
   `CycleCollector.add_stream_dict`.
4. `CycleCollector` детектирует развороты штока (по знаку скорости),
   собирает завершённые циклы (НМТ→ВМТ→НМТ), усредняет/квантует их и
   сообщает о завершении шага программы (`Mode.COLLECT`, `Mode.STROKE_ONLY`,
   `Mode.NMT_FINAL`, `Mode.MID_FINAL`, ...).
5. `Model` считает результат (`CalcData`: макс. усилия отбоя/сжатия, мощность,
   частота поршня), шлёт Qt-сигнал на обновление графика в `AppWindow`.
6. По завершении испытания `Model.save_data_test_in_archive()` /
   `save_temper_test_in_archive()` пишут запись через `WriterArch` в
   `archive/ГГГГ-ММ-ДД.csv`.
7. Команды на привод (пуск/стоп/скорость), лампы индикации и включение записи
   в буфер идут в обратную сторону: `Model` → `Writer.write_out()` → очередь →
   `WriterThread` → Modbus.

## Виды испытаний

`TypeTest` (`scripts/controller/stages.py`):

| Тип | Что делает |
|---|---|
| `LAB` | Лабораторный тест на двух паспортных скоростях амортизатора (`speed_one`/`speed_two`) |
| `LAB_HAND` | Тест на одной скорости, заданной оператором вручную |
| `LAB_CASCADE` | Каскад: последовательный прогон по списку скоростей (`data_test.speed_list`) |
| `CONV` | Конвейерный (приёмочный) тест: два прохода, результат — загорается зелёная/красная лампа по допускам амортизатора |
| `TEMPER` | Температурный тест: непрерывный прогон до достижения целевой температуры (`FINISH_TEMPER`), с накоплением графика усилие/температура |
| `SETTINGS` | Технологический режим окна настроек — прямой просмотр регистров/буфера, коррекция нуля усилия |

Графики считаются в `scripts/calc_graph/`:
- `move_graph.py` — усилие(перемещение) — обычный лабораторный график;
- `boost_graph_one.py` / `boost_graph_two.py` — усилие(скорость), два способа расчёта скорости, для конвейерных/двухскоростных тестов;
- `cascad_graph.py` — усилие отбоя/сжатия от скорости (каскад) с допусками;
- `temper_graph.py` — усилие(температура);
- `triple_graph.py` — комбинированный ход/скорость/усилие от угла поворота кривошипа;
- `compare_graph.py` / `test_graph.py` — наложение нескольких архивных записей друг на друга.

## Machine состояний испытания (Controller/Stage)

`Controller` — табличный конечный автомат (`Stage` → enter/stage/exit
хэндлеры), тикается таймером 100 мс. Упрощённая последовательность обычного
теста:

```
WAIT
 → (жёлтая кнопка) TRAVERSE_REFERENT (поиск референтной точки по концевику)
 → INSTALL_AMORT (подвод траверсы под амортизатор, ожидание повторного
                   нажатия жёлтой кнопки на установку)
 → START_POINT_AMORT (позиционирование под тест)
 → TEST_MOVE_CYCLE (детекция движения) → PUMPING (прогон/прокачка)
 → TEST_SPEED_ONE → TEST_SPEED_TWO   (или TEST_LAB_HAND_SPEED /
                                        TEST_LAB_CASCADE / TEST_TEMPER —
                                        в зависимости от TypeTest)
 → STOP_GEAR_END_TEST (доводка до останова)
 → STOP_GEAR_MIN_POS (доворот до НМТ)
 → WAIT
```

Аварийные переходы (`AlarmSteps`) в любой момент могут прервать
последовательность: `lost_control` (потеря управления), `excess_force`
(превышение усилия), `safety_fence` (ограждение), `excess_temperature`
(перегрев), выход траверсы за концевики (`ALARM_TRAVERSE`).

## Жёлтая кнопка на стенде

Механическая кнопка SB3 (бит 13 регистра 0x2003) для управления без
компьютера. Распознавание — `scripts/yellow_button.py` (`YellowButton`):
срабатывание по факту нажатия с защитой от дребезга (0.1 с) и паузой 1.5 с
между срабатываниями, одно нажатие = одно событие независимо от
длительности. Состояние приходит и из регистров, и из буфера; уровень
«отпущено» выясняется для каждого источника после переключения (в одной из
прошивок кнопка была инвертирована: 0 = нажата). Если «отпущено» = 1, в
логе предупреждение `бит 13 ... инвертирован`. Записи буфера с битом 0 = 0
(буфер перед данными заполнен нулями) для кнопки не учитываются — при
инвертированной кнопке именно они давали ложное нажатие при переходе на
чтение буфера.

Что делает нажатие (`AppWindow.yellow_btn_pressed`) — то же, что активная
экранная кнопка:
- на экране «нажмите ЗАПУСК или жёлтую кнопку» — «ЗАПУСК»;
- идёт испытание — «ПРЕРВАТЬ ИСПЫТАНИЕ»;
- испытание окончено — «НАЗАД» (траверса в точку снятия амортизатора);
- в остальных состояниях (меню, позиционирование, авария) — ничего.

## Настройка хода (остановка шатуна в середине обратного хода)

Кнопка «Настройка хода» проворачивает шатун и останавливает его в середине
обратного хода (ВМТ→НМТ), где доступны регулировочные гайки.
`CycleCollector`, режим `MID_FINAL` (`_try_arm_mid`): точка остановки
считается на развороте в ВМТ как `(НМТ + ВМТ) / 2 + MID_LEAD`, но только
если подъём точно начался из НМТ:
- перед ним был разворот в НМТ после спуска ≥ 10 мм (не дрожание линейки), или
- старт совпал с НМТ, известной по прошлым полным оборотам (± 2 мм).

Иначе ВМТ пропускается — шатун делает лишний оборот, но встаёт верно. После
включения стенда (НМТ ещё неизвестна) настройка хода занимает около 1.75
оборота. Скачок показаний > 5 мм между соседними записями буфера (линейка
прошла референтную точку и перешла в абсолютные координаты) сбрасывает
отслеживание разворотов — накопленное до скачка относится к старым координатам.

## Modbus-протокол

RTU по одному COM-порту (`pymodbus`, `device_id=1`).

- `0x2000`, 14 регистров — «живое» состояние: усилие (float, 2 рег.),
  перемещение штока, слово состояния (`0x2003`, биты — `cycle_force`,
  `red_light`, `green_light`, `lost_control`, `excess_force`,
  `select_temper`, `safety_fence`, `traverse_block`, `state_freq`,
  `state_force`, `yellow_btn`), счётчик записи, перемещение траверсы,
  температура 1, аварийное усилие, температура 2.
- `0x2003` (запись) — то же слово состояния, отдельные биты выставляются
  через `Model._write_reg_state` (буфер вкл/выкл, лампы, сброс блокировок,
  выбор температуры).
- `0x200a` — запись аварийного (максимально допустимого) усилия.
- `0x2005`/входной модуль МВ110-224.16ДН — состояние концевиков траверсы
  (`traverse_block_left/right`, `alarm_highest/lowest_position`,
  `highest/lowest_position`).
- `0x4000+` — кольцевой буфер осциллограммы (усилие/перемещение/состояние/
  температура на каждый отсчёт), читается пачками по 20 записей во время
  теста.
- `0x2061` — «почтовый ящик» для команд частотным преобразователям:
  `FreqControl` формирует Modbus-RTU-кадр для ЧП (адрес, команда,
  CRC16) и пишет его как обычные holding-регистры — то есть контроллер
  стенда транслирует эти регистры дальше на шину ЧП.

Все адреса собраны как именованные константы в `scripts/modbus/registers.py`
— при работе с протоколом смотреть/править туда, а не искать магические
числа по файлам.

## Конфигурация

`.env` в корне проекта + `config.py`. Сам `.env` в git не хранится: у каждой
машины свой COM-порт и таймаут. Шаблон со значениями стенда лежит в `.env.example`:

```powershell
copy .env.example .env
```

| Переменная | Смысл | Пример |
|---|---|---|
| `COM` | COM-порт | `COM12` |
| `BAUDRATE` | Скорость порта | `460800` |
| `TIMEOUT` / `RETRIES` | Таймаут (с) и число повторов Modbus-запроса. Для эмулятора нужно `0.1`, см. [Запуск](#запуск) | `0.02` / `1` |
| `PAUSE_REG` / `PAUSE_BUF` / `PAUSE_WRITE` | Паузы между опросами/записью (см. [известные проблемы](#известные-проблемы-и-todo) — сейчас часть пауз отключена) | |
| `CONST_TRAV` | Константа положения траверсы (мм), точка отсчёта для позиционирования | `760` |
| `FREQ` | Марка частотника: `E` — Evra, `D` — Delta | `E` |
| `LOG_LEVEL` | Уровень логирования (`10`=DEBUG, `20`=INFO) | `10` |
| `FORCE_KOEF` | Калибровочный коэффициент датчика усилия | `0.89766` |
| `FINISH_TEMPER` | Целевая температура окончания температурного теста, °C | `80` |
| `MID_LEAD` | Упреждение остановки шатуна при настройке хода, мм: «стоп» подаётся раньше середины обратного хода на столько, чтобы выбегом дойти до неё (≈ 13 мм — измеренный выбег при ходе 100 и медленной скорости 0.02 м/с). Фактическое отклонение от середины пишется в лог на уровне DEBUG | `13` |
| `BUFFER_TIMEOUT` | Страховка буфера: секунд без новых данных из буфера (пока он включён, контроллер пишет запись каждую 1 мс) или без подтверждения `buffer_on`, после чего буфер перезапускается (выкл → вкл) с возвратом на тот же этап | `5` |
| `BUFFER_RESTARTS` | Страховка буфера: перезапусков подряд без данных, после чего авария «НЕТ ДАННЫХ ОТ КОНТРОЛЛЕРА» со стопом привода. Каждый перезапуск — WARNING в логе (`Страховка буфера: ...`) | `3` |
| `SPEED_TOLERANCE` | Допуск набора скорости испытания, %. После смены скорости сбор начинается, только когда фактическая скорость (π · ход / период оборота, по данным буфера) два оборота подряд в допуске от заданной. Заданная/фактическая скорость каждого шага — INFO в логе | `5` |
| `SPEED_WAIT_CYCLES` | Сколько оборотов ждать набора скорости. Дальше сбор идёт как есть; если и собранный оборот вне допуска — в конце испытания сообщение оператору с фактической скоростью (в окне и архиве остаётся заданная) | `10` |
| `ALARM_FILTER_READS` | Фильтр аварий от помех (прежнее имя `TRAVERSE_ALARM_READS` тоже понимается): **концевики траверсы, ограждение и перегрев** засчитываются, только если сигнал держится столько чтений подряд (одно чтение ≈ 20–50 мс). Короче — помеха, WARNING «…: сигнал аварии N чтение(я) и пропал — помеха» в логе. Перегрев — по текущей температуре, а «Макс температура» испытания — по медиане трёх последних чтений (одиночный выброс датчика не попадает ни в аварию, ни в архив). Потеря управления и превышение усилия **не фильтруются**: их фиксирует и держит контроллер, привод он уже заблокировал. Повод: 12.10 одно чтение концевика при разгоне до 0.9 м/с дало ложную аварию при траверсе на месте. Настоящая авария траверсы останавливает привод и испытание, как остальные | `3` |
| `ALARM_FILTER_MS` | Фильтр аварий от помех по времени: те же аварии засчитываются, только если сигнал держится и не меньше `ALARM_FILTER_READS` чтений, и не меньше стольких миллисекунд (по последнему чтению с сигналом). Чтение регистров идёт каждые несколько мс, поэтому 3 чтения — это ≈ 10–15 мс, мало против дребезга концевика траверсы от вибрации на высокой скорости (ложное «верхнее аварийное положение» при неподвижной траверсе). В WARNING о помехе пишется длительность сигнала в мс — по ней подбирать значение | `200` |
| `TURN_HYST_MM` | Развороты шатуна (НМТ/ВМТ, границы оборотов при сборе): разворот засчитывается, когда шатун отошёл от последнего экстремума на столько мм; время и положение разворота — в самом экстремуме. Шум линейки ±0.1 мм до этого не дотягивается. `0` — старое определение по знаку скорости с плавающим порогом: оно теряло развороты, и собранный «оборот» бывал 1.5–2 настоящих (двойная петля на графике, «Скорость испытания … −48 %» в логе; 19.10 — 4 записи архива). Проверка по записям буфера 16 и 19.10 (`tools/buffer_dump/check_turns.py`): старое — 45 двойных и 5 укороченных оборотов из 578, новое — 0 из 702 | `1.0` |
| `STOP_WINDOW_MS` / `STOP_SPAN_MM` | Остановка шатуна после «стоп» в конце испытания (перед доводкой до НМТ): ЧП закончил торможение, если за последние `STOP_WINDOW_MS` мс (записей буфера) положение сдвинулось не больше чем на `STOP_SPAN_MM` мм. Не полная неподвижность: после торможения шатун может десятки секунд ползти 2–3 мм/с под действием амортизатора (19.10, ход 100). По записи 19.10 — «стоп» через 2–2.5 с после команды при скорости шатуна 0–2 мм/с. В лог (INFO): «Шатун остановился через N с после команды «стоп», положение …» | `500` / `2.0` |
| `STOP_TIMEOUT` | Шатун не остановился за столько секунд после «стоп» — команда повторяется, WARNING «Шатун не остановился …» | `10` |
| `BUFFER_DUMP` | Диагностика: `1` — запись сырого потока буфера и событий обмена (команды и подтверждения buffer_on/off, бит 0 по регистрам, этапы, команды ЧП, события коллектора, аварии) в `logs/buffer/ГГГГ-ММ-ДД/ЧЧ-ММ-СС_<операция>.csv`, файл на операцию стенда (испытание, определение/настройка хода, окно отладки). Около 40 байт на запись буфера: 2–4 МБ на обычное испытание. Сами файлы не удаляются — включать на время сбора данных. Разбор: `uv run tools/buffer_dump/analyze.py logs/buffer/ГГГГ-ММ-ДД` (`-v` — подробно, `--csv DIR` — выгрузка записей) | `0` |

Справочники амортизаторов (`amorts.ini`) и операторов (`operators.ini`)
редактируются из соответствующих окон GUI и хранятся рядом с exe.

Профили каскадного испытания (`cascade.ini`, тоже рядом с exe) правятся
вручную в текстовом редакторе. Кнопки «Профиль 1..4» на странице
спецификации заполняют таблицу скоростей:

```ini
[Profile1]
name = Профиль 1
speeds = 0.05; 0.1; 0.15; 0.2; 0.25; 0.3
```

`name` — подпись кнопки, `speeds` — скорости в м/с через `;`, не больше 30.
Комментарии пишутся только отдельной строкой: всё после `=` идёт в значение.

Файл перечитывается при каждом нажатии кнопки. Скорости вне диапазона
от 0.02 до максимальной для хода амортизатора пропускаются с предупреждением.
Скорости каскада должны строго возрастать: повтор или убывание ломают
интерполяцию графика усилие/скорость. Это проверяется при ручном добавлении
скорости, при заполнении из профиля (профиль с ошибкой не загружается) и
перед стартом испытания — оператору показывается предупреждение.
При смене амортизатора таблица перепроверяется: если она заполнена профилем,
то перезаполняется им же под новый ход; если её правили вручную, из неё
удаляются скорости, недопустимые для нового хода.

Если `cascade.ini` удалить, программа создаст его заново при запуске или при
нажатии кнопки профиля. Значения по умолчанию берутся из
`CascadeProfiles.DEFAULT_CONTENT` (`scripts/cascade_profiles.py`), в лог
пишется предупреждение.

## Запуск

Окружение управляется через [uv](https://docs.astral.sh/uv/): зависимости —
в `pyproject.toml`, точные версии зафиксированы в `uv.lock`, версия Python
(3.11) — в `.python-version`. Python отдельно ставить не нужно, uv скачает
его сам.

```powershell
uv sync                    # создать .venv и поставить зависимости (вместе с dev-группой)
copy .env.example .env     # при первом запуске, затем поправить COM-порт
uv run main.py
```

Добавить или обновить пакет: `uv add <пакет>` / `uv lock --upgrade-package <пакет>`,
после этого закоммитить `pyproject.toml` и `uv.lock`.

Для запуска нужен реальный стенд на указанном COM-порту либо эмулятор.
Если подключиться не удалось, приложение стартует, но обмен с
контроллером не работает (см. [известные проблемы](#известные-проблемы-и-todo)
про `Client.connect_client`).

### Работа без стенда (эмулятор)

1. Создать виртуальную пару COM-портов через com0com, например COM3 ↔ COM4.
2. Запустить Modbus Slave, открыть проект из `MBSlave/` (регистры с `0x2000`,
   буфер с `0x4000`) и подключить его к одному порту пары (COM3): RTU,
   460800 8N1, Slave ID 1.
3. В `.env` указать второй порт пары (`COM = COM4`) и `TIMEOUT = 0.1`.

Таймаут `0.02` подходит только для реального контроллера: эмулятор через
виртуальный порт отвечает за 30–50 мс. С `0.02` ответов нет вообще, а в логе
сыплется `No response received ... CLOSING CONNECTION`.

Приложение — синглтон (`tendo.singleton`): повторный запуск второй копии
ничего не сделает.

PyInstaller стоит в dev-группе (`uv sync` ставит его сам). Раньше собирали

## Архив и логи

- `archive/ГГГГ-ММ-ДД.csv` — архив испытаний за день (имена с года сортируются по
  дате; в окне архива дата показывается как ДД.ММ.ГГГГ; старые файлы
  ДД.ММ.ГГГГ.csv переименовываются при запуске, `scripts/archive_names.py`),
  открывается в Excel
  напрямую (Windows-1251: Excel на стенде UTF-8 не понимает даже с BOM;
  разделитель `;`, десятичная запятая). Формат —
  2 строки на запись (метаданные + первый график, затем строка `*` + второй
  график), испытание закрывается строкой `end_test`. Каждая скорость
  лабораторного/конвейерного испытания и каждый шаг каскада — отдельная
  запись (шаги каскада видны и в «Лабораторном», и собранными в «Каскаде»).
  Парсится обратно в `archive.py` (`ReadArchive`) в pydantic-схемы
  `LabSchema`/`ConvSchema`/`TempSchema`/`CascSchema`.
- Запись (`scripts/archive_saver.py`, `WriterArch`) — один фоновый поток с
  очередью, порядок строк сохраняется:
  - файл открыт в Excel → запись повторяется раз в секунду, пока файл не
    освободится, оператору в статусбар выводится просьба закрыть файл;
  - при закрытии программы очередь дописывается (до 10 с);
  - при старте каждого испытания, если последнее в файле не закрыто
    `end_test` (вылет программы и т.п.), он дописывается — испытания при
    чтении не склеиваются. Плюс `end_test` пишется на всех путях остановки
    (`Model.write_end_test_in_archive`, флаг `flag_archive_test_open`
    защищает от двойной записи);
  - прерванное температурное испытание (кнопки, аварии) сохраняется с уже
    накопленными точками (`Model.close_test_in_archive`), если есть хоть одна;
  - старые файлы в UTF-8 (с BOM и без) при запуске перекодируются в 1251,
    занятый в этот момент файл — перед первой дозаписью; читалка понимает
    обе кодировки;
  - `;` в названии/серийнике/ФИО заменяется на `,`.
- **Правка архива в Excel** (например, исправить серийник) возможна, программа
  такой файл прочитает (кодировку определяет сама; `end_test;;;;` и время
  `9:09:12` вместо `09:09:12` после Excel ей не мешают). Но Excel при открытии
  сам переделывает значения **во всём файле**, поэтому:
  1. Сохранять как «CSV (разделители — запятые) (*.csv)» (Windows-1251, как
     пишет программа; «CSV UTF-8» программа тоже прочитает и при запуске
     перекодирует). **Не в .xlsx** — такой файл программа не увидит.
  2. Серийники/названия, похожие на даты или числа, Excel испортит при
     сохранении: `1-2`, `1.1`, `1/2` → даты (`01.фев`), `007` → `7`, `254.00` →
     `254`. На 2026-10-12 в архиве такие серийники: `1-2, 1.1, 1.2, 1/1, 1/2, 1/3,
     1/4, 2-1, 3-1, 4-1`. Обход — открывать через «Данные → Из текста/CSV» и
     задать колонкам «Название гасителя» и «Серийный номер» тип «Текстовый».
  3. В Excel не больше 16 384 колонок. Самая длинная строка в архиве — 14 253
     (20.08), но на 0.02 м/с при ходе больше ~105 мм оборот длиннее 16 000
     точек. Если Excel при открытии предупреждает, что файл загружен не
     полностью, — **не сохранять**, иначе графики этих испытаний обрежутся.
  4. Править между испытаниями: пока файл открыт в Excel, программа не может
     в него писать и ждёт (просьба закрыть файл в статусбаре).
  5. Мелочь: у самой длинной строки файла после Excel пропадает завершающий
     `;`, и читалка (`archive_list[...:-1]`) теряет одну последнюю точку графика.

  Для разовых правок надёжнее править файл скриптом, меняя только нужные поля
  (так делалось 2026-10-12: удаление ложного `end_test`, удаление испытания).
- `logs/ГГГГ-ММ-ДД.log` (старые ДД_ММ_ГГГГ.log переименовываются при запуске) — общий лог приложения (уровень из `LOG_LEVEL`).
  При странном поведении стенда — первым делом сюда: `grep ERROR` по
  сегодняшнему файлу почти всегда указывает прямо на причину (так были
  найдены оба бага ниже).

### 1. ~~Авария по концевикам траверсы фактически не отрабатывала~~ — исправлено

`scripts/controller/alarm_steps.py`, `AlarmSteps.step_alarm_traverse_position`
вызывал `self._set_common_alarm_flags(self, msg)` — лишний `self` вторым
позиционным аргументом (метод ожидает только `tag`). Это бросало
`TypeError`, который гасился внешним `try/except`, из-за чего код ниже
**не выполнялся**:

```python
self.model.write_bit_red_light(1)
self.model.stop_collect()
self.signals.alarm_traverse.emit(tag)
```

То есть при выходе траверсы за концевик (`alarm_highest_position` /
`alarm_lowest_position`) не включалась красная лампа, не останавливался
сбор данных и не долетал сигнал, по которому оператору должно
показываться предупреждение с кнопкой «ОПУСТИТЬ»/«ПОДНЯТЬ»
(`app/wins/view.py: btn_ok_message_clicked` → `TraverseService.
traverse_move_out_alarm`). Авария «наступала» тихо (флаг
`flag_alarm_traverse` взводился и дальше не сбрасывался), без видимой
реакции стенда — стенд выглядел «зависшим» на концевике. **Было
подтверждено в `logs/29_05_2026.log`**:
```
[ERROR] - (alarm_steps.py).step_alarm_traverse_position(117) -
AlarmSteps._set_common_alarm_flags() takes 2 positional arguments but 3 were given
```
Исправлено: лишний `self` убран, `_set_common_alarm_flags(msg)`.

### 3. ~~`Client.connect_client()` всегда считал соединение установленным~~ — исправлено

Было:
```python
self.client.connect()
self.flag_connect = True
```
Возврат `connect()` (bool успеха) игнорировался — `flag_connect` был всегда
`True`, даже если порт не открылся (занят, не существует, стенд выключен).
`Model._start_param_model()` проверяет именно этот флаг перед стартом

Исправлено: `self.flag_connect = bool(self.client.connect())` (плюс защита
на случай, если сам клиент не создался).

  self.logger.error(e)` — гасит исключение и не даёт traceback (местами
  используется `logger.exception`, но не всегда). Это удобно для того,
  чтобы стенд не падал целиком на любой мелкой ошибке, но затрудняет
  диагностику: именно так авария из п.1 «зависла» в проде на несколько
  дней, прежде чем стала заметна.

### 7. ~~Стенд останавливался и не доворачивал до НМТ~~ — исправлено

По логам стенда за март–сентябрь ~20 случаев: этап `STOP_GEAR_END_TEST`
(«стоп, ждём остановки привода») не переходил в доворот до НМТ, пока
оператор не прерывал его (от секунд до минут). Причина — гонка при
переходе через `WAIT_BUFFER`: `_stage_wait_buffer` проверял бит «буфер
включён» в последнем прочитанном состоянии, а после испытания он ещё горел
от прошлой сессии буфера. Чтение буфера перезапускалось с 0x4000 до того,
как контроллер выполнил `buffer_off`/`buffer_on` и перезапустил буфер
(в логе 28.07 12:59:35: переход в 35.688, `buffer_on` выполнен в 35.946).
Читалка брала первую (старую) запись за точку отсчёта, номера новых записей
с ней не стыковались, данные не шли, остановка привода не определялась.
Исправлено: `WAIT_BUFFER` ждёт подтверждения записи именно команды
`buffer_on` (сигнал `Writer.check_buffer`), а не бит состояния.
Плюс страховка (`Controller._check_buffer_watchdog`): если данных из буфера
нет `BUFFER_TIMEOUT` секунд (или `buffer_on` не подтверждается), буфер
перезапускается; после `BUFFER_RESTARTS` неудачных попыток — авария со
стопом привода (раньше привод в такой ситуации так и крутился).

### 8. TODO: выталкивающая сила на графиках усилия

Решено (2026-10-10): на графиках усилия учитывать выталкивающую силу так же,
как в цифрах отбоя/сжатия, — тогда диаграмма Лампе проходит через начало
координат («касается оси X» на развороте штока), а пик на графике совпадает
с цифрой. Сейчас:

| График | Выталкивающая сила |
|---|---|
| цифры отбоя/сжатия (испытание и архив) | **учитывается**: `abs(round(max/min + push_force, 2))` |
| живой график испытания (`TestGraph`, `update_lab_graph`/`update_conv_graph`) | не учитывается — рисуется `data_test.force` (коэффициент датчика + его ноль, без выталкивающей) |
| архив: «Усилие/Перемещение» (`MoveGraph`) | не учитывается |
| архив: «Усилие/Скорость №1 и №2» (`BoostGraphOne/Two`) | не учитывается |
| архив: каскад (`CascadeGraph.calc_graph`) | **учитывается** (к точкам отбоя/сжатия) |
| температурное: живой график и архив (`TemperGraph`) | **учитывается** — точки отбоя/сжатия это уже цифры с выталкивающей силой (исправлено 2026-10-10, см. ниже) |
| архив: тройной (`TripleGraph`) | не учитывается — **и не нужно** (решение заказчика) |

Температурное испытание, исправлено 2026-10-10: (1) `TemperGraph` прибавлял
выталкивающую силу второй раз к точкам, где она уже учтена; (2) с 22.05
лабораторное переворачивает знак усилия (`not_avarage_cycles`), а
температурное вместо этого меняло местами отбой/сжатие — ноль датчика и
выталкивающая сила учитывались с обратным знаком (отбой R − p вместо R + p,
сжатие |C| + p вместо |C| − p, плюс удвоенная поправка нуля). Теперь оба
испытания считаются одинаково (`_pars_result_temper_test` переворачивает знак,
отбой/сжатие по модулю — на графике оба положительные). **Старые
температурные записи архива** (между 19.05 и этим исправлением) точно не
пересчитать — ноль датчика в архив не пишется; при сравнении с новыми
учитывать сдвиг ≈ ±2 × выталкивающая сила.

Сделать: прибавлять `push_force` (`CalcGraphValue.select_push_force` —
статическая или динамическая по флагу) к `force_list` в `MoveGraph`,
`BoostGraphOne`, `BoostGraphTwo` (вместе с ними — сравнение графиков в
`CompareGraph`, оно использует те же классы) и, для единообразия, в живом
графике испытания. Пример масштаба (архив 09.10, 0.4 м/с, статическая 19 кгс):
пик на графике 245 кгс против цифры отбоя 264; при нулевой скорости на графике
−10…−26 кгс вместо ≈0.

Знак: в цифрах сжатие тоже считается как `abs(min + push_force)`, т.е.
сдвиг один и тот же для всей кривой — `force + push_force`.
