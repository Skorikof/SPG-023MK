# SPG-023MK — ПО управления испытательным стендом амортизаторов

Настольное приложение (Windows, PySide6) для управления испытательным стендом
SPG-023MK: разгон/торможение амортизатора через частотные преобразователи,
чтение усилия/перемещения/температуры по Modbus, построение графиков испытаний
и ведение архива результатов.

> для дальнейшей поддержки. Раздел [«Известные проблемы»](#известные-проблемы-и-todo)

## Что делает стенд

Амортизатор зажимается между траверсой (подвижная каретка, задаёт исходную
точку под конкретную длину амортизатора) и приводом, который циклически
двигает шток через кривошипный механизм. Стенд меряет усилие на штоке,
перемещение штока и температуру (двух точек), пока привод крутится с
заданной скоростью, и по данным одного или нескольких циклов строит график
усилие/перемещение (и производные от него: усилие/скорость, усилие/температура
и т.д.).

Управляют этим два частотных преобразователя (ЧП, «Evra» или «Delta» — выбор
в конфиге) через один и тот же COM-порт:
- адрес 1 — приводной двигатель (крутит кривошип/шток);
- адрес 2 — привод траверсы (позиционирование по высоте).

## Архитектура

```
main.py
 └─ AppWindow (app/wins/view.py)       — главное окно, графики, кнопки
     ├─ Model (scripts/model.py)       — состояние стенда, данные испытания,
     │                                    парсинг Modbus-ответов, запись команд
     ├─ Controller (scripts/controller/controller.py)
     │                                  — конечный автомат испытания (Stage)
     │   ├─ AlarmSteps                 — обработка аварий
     │   └─ TraverseService            — позиционирование траверсы
     └─ дочерние окна (архив, амортизаторы, операторы, настройки)

Model
 ├─ Client (scripts/modbus/client.py)       — pymodbus RTU-клиент, COM-порт
 ├─ Reader (scripts/reader.py)              → ReaderThread (my_thread/thread_reader.py)
 ├─ Writer (scripts/writer.py)              → WriterThread (my_thread/thread_writer.py)
 ├─ WriterArch (scripts/archive_saver.py)   → WriterArchive — запись CSV в archive/
 ├─ ParserSPG023MK (scripts/parser/parser.py) — регистры → физические величины
 ├─ CalcData (scripts/data_calculation.py)    — математика (усреднение циклов,
 │                                               мощность, частота поршня и т.д.)
 └─ CycleCollector (scripts/controller/cycle_collector.py)
                                               — детектор циклов/разворотов штока,
                                                 усреднение, точное позиционирование
```

`Reader`/`Writer`/`WriterArch` — это диспетчеры очереди в главном Qt-потоке;
сама работа с портом (чтение регистров, отправка команды ЧП, запись строки в
CSV) выполняется в фоновых `QRunnable`-задачах (`ReaderThread`, `WriterThread`,
`WriterArchive`) из `scripts/my_thread/`, а результат прилетает обратно через
Qt-сигналы (thread-safe).

## Поток данных

1. `ReaderThread` в фоновом потоке непрерывно читает 14 holding-регистров с
   `0x2000` (усилие, перемещение, биты состояния, температуры, счётчик) —
   режим `'reg'`.
2. Во время активного испытания (`buffer_on`, бит 0 регистра `0x2003`)
   переключается в режим `'buffer'` и вычитывает кольцевой буфер осциллограммы
   с `0x4000` — по 20 записей × 6 регистров за раз, отслеживая
   последовательность по счётчику записи, пока `Model`/`CycleCollector` не
   соберут нужное число циклов.
3. `Model._reader_result` парсит ответ через `ParserSPG023MK`, обновляет
   `state_dict`/`switch_dict`, и в режиме буфера передаёт поток точек в
   `CycleCollector.add_stream_dict`.
4. `CycleCollector` детектирует развороты штока (по знаку скорости),
   собирает завершённые циклы (НМТ→ВМТ→НМТ), усредняет/квантует их и
   сообщает о завершении шага программы (`Mode.COLLECT`, `Mode.STROKE_ONLY`,
   `Mode.NMT_FINAL`, `Mode.MID_FINAL`, ...).
5. `Model` считает результат (`CalcData`: макс. усилия отбоя/сжатия, мощность,
   частота поршня), шлёт Qt-сигнал на обновление графика в `AppWindow`.
6. По завершении испытания `Model.save_data_test_in_archive()` /
   `save_temper_test_in_archive()` пишут запись через `WriterArch` в
   `archive/ДД_ММ_ГГГГ.csv`.
7. Команды на привод (пуск/стоп/скорость), лампы индикации и включение записи
   в буфер идут в обратную сторону: `Model` → `Writer.write_out()` → очередь →
   `WriterThread` → Modbus.

## Виды испытаний

`TypeTest` (`scripts/controller/stages.py`):

| Тип | Что делает |
|---|---|
| `LAB` | Лабораторный тест на двух паспортных скоростях амортизатора (`speed_one`/`speed_two`) |
| `LAB_HAND` | Тест на одной скорости, заданной оператором вручную |
| `LAB_CASCADE` | Каскад: последовательный прогон по списку скоростей (`data_test.speed_list`) |
| `CONV` | Конвейерный (приёмочный) тест: два прохода, результат — загорается зелёная/красная лампа по допускам амортизатора |
| `TEMPER` | Температурный тест: непрерывный прогон до достижения целевой температуры (`FINISH_TEMPER`), с накоплением графика усилие/температура |
| `SETTINGS` | Технологический режим окна настроек — прямой просмотр регистров/буфера, коррекция нуля усилия |

Графики считаются в `scripts/calc_graph/`:
- `move_graph.py` — усилие(перемещение) — обычный лабораторный график;
- `boost_graph_one.py` / `boost_graph_two.py` — усилие(скорость), два способа расчёта скорости, для конвейерных/двухскоростных тестов;
- `cascad_graph.py` — усилие отбоя/сжатия от скорости (каскад) с допусками;
- `temper_graph.py` — усилие(температура);
- `triple_graph.py` — комбинированный ход/скорость/усилие от угла поворота кривошипа;
- `compare_graph.py` / `test_graph.py` — наложение нескольких архивных записей друг на друга.

## Machine состояний испытания (Controller/Stage)

`Controller` — табличный конечный автомат (`Stage` → enter/stage/exit
хэндлеры), тикается таймером 100 мс. Упрощённая последовательность обычного
теста:

```
WAIT
 → (жёлтая кнопка) TRAVERSE_REFERENT (поиск референтной точки по концевику)
 → INSTALL_AMORT (подвод траверсы под амортизатор, ожидание повторного
                   нажатия жёлтой кнопки на установку)
 → START_POINT_AMORT (позиционирование под тест)
 → TEST_MOVE_CYCLE (детекция движения) → PUMPING (прогон/прокачка)
 → TEST_SPEED_ONE → TEST_SPEED_TWO   (или TEST_LAB_HAND_SPEED /
                                        TEST_LAB_CASCADE / TEST_TEMPER —
                                        в зависимости от TypeTest)
 → STOP_GEAR_END_TEST (доводка до останова)
 → STOP_GEAR_MIN_POS (доворот до НМТ)
 → WAIT
```

Аварийные переходы (`AlarmSteps`) в любой момент могут прервать
последовательность: `lost_control` (потеря управления), `excess_force`
(превышение усилия), `safety_fence` (ограждение), `excess_temperature`
(перегрев), выход траверсы за концевики (`ALARM_TRAVERSE`).

## Modbus-протокол

RTU по одному COM-порту (`pymodbus`, `device_id=1`).

- `0x2000`, 14 регистров — «живое» состояние: усилие (float, 2 рег.),
  перемещение штока, слово состояния (`0x2003`, биты — `cycle_force`,
  `red_light`, `green_light`, `lost_control`, `excess_force`,
  `select_temper`, `safety_fence`, `traverse_block`, `state_freq`,
  `state_force`, `yellow_btn`), счётчик записи, перемещение траверсы,
  температура 1, аварийное усилие, температура 2.
- `0x2003` (запись) — то же слово состояния, отдельные биты выставляются
  через `Model._write_reg_state` (буфер вкл/выкл, лампы, сброс блокировок,
  выбор температуры).
- `0x200a` — запись аварийного (максимально допустимого) усилия.
- `0x2005`/входной модуль МВ110-224.16ДН — состояние концевиков траверсы
  (`traverse_block_left/right`, `alarm_highest/lowest_position`,
  `highest/lowest_position`).
- `0x4000+` — кольцевой буфер осциллограммы (усилие/перемещение/состояние/
  температура на каждый отсчёт), читается пачками по 20 записей во время
  теста.
- `0x2061` — «почтовый ящик» для команд частотным преобразователям:
  `FreqControl` формирует Modbus-RTU-кадр для ЧП (адрес, команда,
  CRC16) и пишет его как обычные holding-регистры — то есть контроллер
  стенда транслирует эти регистры дальше на шину ЧП.

Все адреса собраны как именованные константы в `scripts/modbus/registers.py`
— при работе с протоколом смотреть/править туда, а не искать магические
числа по файлам.

## Известные проблемы и TODO

Ниже — то, что уже подтверждено чтением кода и логов

### 1. ~~Авария по концевикам траверсы фактически не отрабатывала~~ — исправлено

`scripts/controller/alarm_steps.py`, `AlarmSteps.step_alarm_traverse_position`
вызывал `self._set_common_alarm_flags(self, msg)` — лишний `self` вторым
позиционным аргументом (метод ожидает только `tag`). Это бросало
`TypeError`, который гасился внешним `try/except`, из-за чего код ниже
**не выполнялся**:

```python
self.model.write_bit_red_light(1)
self.model.stop_collect()
self.signals.alarm_traverse.emit(tag)
```

То есть при выходе траверсы за концевик (`alarm_highest_position` /
`alarm_lowest_position`) не включалась красная лампа, не останавливался
сбор данных и не долетал сигнал, по которому оператору должно
показываться предупреждение с кнопкой «ОПУСТИТЬ»/«ПОДНЯТЬ»
(`app/wins/view.py: btn_ok_message_clicked` → `TraverseService.
traverse_move_out_alarm`). Авария «наступала» тихо (флаг
`flag_alarm_traverse` взводился и дальше не сбрасывался), без видимой
реакции стенда — стенд выглядел «зависшим» на концевике. **Было
подтверждено в `logs/29_05_2026.log`**:
```
[ERROR] - (alarm_steps.py).step_alarm_traverse_position(117) -
AlarmSteps._set_common_alarm_flags() takes 2 positional arguments but 3 were given
```
Исправлено: лишний `self` убран, `_set_common_alarm_flags(msg)`.

### 2. Увеличение номера партии на конвейерном тесте не переживает буквенный суффикс

`app/wins/view.py:974`, `cancel_test_conv_clicked`:

```python
self.model.data_test.serial = str(int(self.model.data_test.serial) + 1)
```

Если серийный номер содержит не только цифры (в логах встречались `'1п'`,
`'2п'`), `int()` падает с `ValueError`, и кнопка «НАЗАД» на конвейерном
тесте перестаёт работать (проверено — 15 срабатываний за секунды в логе,
похоже на то, что оператор нажимал повторно, думая, что кнопка не
реагирует).

**Решение (пока):** это автоинкремент есть только в конвейерном режиме, и
буквенный суффикс там считается ошибкой ввода оператора — серийник должен
быть числом. Пока не меняли поведение кода (валидацию поля добавим позже,
когда определимся, как обыграть суффиксы вроде «п»); просто держим в виду,
что оператору нужно вводить в конвейерном тесте только число.

### 3. ~~`Client.connect_client()` всегда считал соединение установленным~~ — исправлено

Было:
```python
self.client.connect()
self.flag_connect = True
```
Возврат `connect()` (bool успеха) игнорировался — `flag_connect` был всегда
`True`, даже если порт не открылся (занят, не существует, стенд выключен).
`Model._start_param_model()` проверяет именно этот флаг перед стартом
ридера/райтера — то есть при недоступном порте программа всё равно
пыталась запустить чтение/запись, вместо понятной ошибки подключения.
Исправлено: `self.flag_connect = bool(self.client.connect())` (плюс защита
на случай, если сам клиент не создался).

  (`writer_flag_init`) — не стали трогать сейчас без стенда под рукой,
  слишком легко тихо сломать очередь записи команд.

### 5. Сделано в рамках лёгкой чистки (без стенда, поведение не менялось)

- Адреса Modbus-регистров (`0x2000`, `0x2003`, `0x200a`, `0x2060`,
  `0x2061`, `0x4000`, ...) были магическими числами в разных файлах —
  вынесены в `scripts/modbus/registers.py` (именованные константы),
  `thread_reader.py`/`thread_writer.py`/`model.py` теперь используют их.
- Убраны неиспользуемые классы `DataMoveGraph`, `DataTemprGraph`,
  `DataSpeeds` из `scripts/test_obj.py` (нигде не были задействованы).
- Убран закомментированный дублирующий код сборки `CascSchema` в
  `scripts/archive.py` (`_create_object_archive`).

### 6. Прочие замеченные моменты (не факт, что это проблема — но стоит держать в голове)

- `scripts/my_thread/thread_reader.py` — паузы `time.sleep(PAUSE_REG)` /
  `time.sleep(PAUSE_BUF)` в цикле опроса закомментированы, то есть регистры
  читаются в busy-loop без искусственной паузы (ограничены только
  временем самого Modbus-обмена). Не факт, что это баг — но `.env`
  по-прежнему определяет `PAUSE_REG`/`PAUSE_BUF`, как будто пауза должна
  быть, и не используется. Трогать без стенда рискованно (может влиять на
  тайминг чтения буфера во время активного теста).
- Почти везде используется паттерн `try/except Exception as e:
  self.logger.error(e)` — гасит исключение и не даёт traceback (местами
  используется `logger.exception`, но не всегда). Это удобно для того,
  чтобы стенд не падал целиком на любой мелкой ошибке, но затрудняет
  диагностику: именно так авария из п.1 «зависла» в проде на несколько
  дней, прежде чем стала заметна.
